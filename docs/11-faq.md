# 11 · FAQ

## 1. 为什么不直接用数据库 / DVC / DataLad / ELN？

它们解决的是不同问题：

- **数据库**：适合多写入者、强事务、频繁查询。小团队没有 DBA，服务挂了会让“数据在但找不到”。
- **DVC/DataLad**：适合大文件版本化与 git 集成，但仍要求你**先有可读的标识**；
  它们不会替你决定“哪个样品、什么条件”。
- **ELN/LIMS**：适合实验记录与流程管理，但通常不覆盖仪器原始文件、仿真产物、
  跨团队共享盘，也不解决“百万文件里怎么找”。

这套东西是**文件系统层的最小治理**：不替换上述任何系统，只保证“文件名 + 清单 + 注册表”
这三样在任何工具之外仍然成立。你可以把它当 ELN 的底层命名/入库层。

## 2. 文件名太长，人记不住怎么办？

人不需要记住。人只需要记住四个区的位置；具体码用补全/速查表。
工具会在报错时给出“该写什么”的提示。

如果长度真的成问题，先砍条件码数量（≤8 是上限，不是目标），
再考虑把“条件”拆成多个文件而不是一个名字里塞更多 code。**不要**为了短而牺牲唯一性。

## 3. 现有上百万文件怎么迁移？

三步：

1. **扫描**：分词、统计槽位覆盖率、找“条件在哪”（文件名/目录/内容头）。
2. **定 cutoff**：某天之后的新文件必须合规；老文件按批次迁移，不搞一夜全改。
3. **按批改名**：预演 → 本人点头 → apply → 改名日志。改名日志是原名唯一留档。

真实案例里，扫描 175 万文件后发现“某个人的条件全在目录名里”，
如果先写规范再扫描，会设计出一套根本落不了地的字段。

## 4. 小团队谁来当 Steward？

一个**愿意为“谁批准”负责**的人，不一定是技术最强的人。
职责是：签字、收库、抽查、放行、维护真值链。

不能是“大家轮流”。签字权必须唯一，否则等于没人签。
如果团队只有 2 人，Steward 可以兼 owner，但**不能审自己交的那批**。

## 5. 能不能让 AI 自动改名？

AI 可以：产改名清单、预演、解释每个错、把全量清单转成 CSV。
AI 不可以：在没有本人点头的情况下 `--apply`。

原因跟“AI 可不可靠”关系不大。**改名会动真实数据，且原名唯一留档。**
工具的五道闸门只审新名字一侧；“新旧对不对得上”没有任何程序在查，人眼是唯一那道。
真实事故里，文件名错了、内容里的编号才是对的——那是唯一破案线索；
AI 为了消错把内容改成和错误文件名一致，就是销毁证据。

## 6. WARN 为什么不能“改”？

因为 WARN 问的是**只有本人知道的事实**：

- RUN 断号：丢了？漏传？有意不交？
- 时间戳大簇：T 是真实采集时间，还是改名当天填的？
- 内容编号不符：哪边是对的？

AI 去“改”，实际是在伪造采集轮次、编时间、伪造内外一致。
**WARN 的出口是台账（answer 列），不是文件。**

## 7. 签字为什么不写在条目里？

写在条目里，`APPROVED` 只是一个字符串：改了内容它还在，AI 可以把它填成“合伙人”，
没有人能证明批准的是哪一版。真实团队为此撤销过整批 162 条签字。

公开版把签字移到 `signatures.yaml`，绑定条目内容的 sha256。改一个字，签名自动失效。
代价是读的时候要 join 两个文件；对几十到几百条的小注册表，这个代价可以接受。

## 8. 为什么不做 Web 看板？

看板是另一个要维护的系统、另一套权限、另一个会过期的真相。
小团队真正要回答的是“谁欠什么”，群里的定时播报 + 一份 `manifest.tsv` 就够了。

需要趋势时，从 manifest 生成一张图；不要把“看图”变成日常流程。

## 9. 机器人为什么不主动 @ 人？

主动 @ 会制造压力，也会制造误报：牌面是早上 8 点的，收库在中午之后；
中间几个小时同事可能已经做完了。照旧牌面催办，比不催更糟。

规则：**先刷牌面，再出卡**；没事也发绿卡（“没收到卡”本身是一个信号）；
未接住的题由日报私发 Steward，不进群。

## 10. 不用飞书能用吗？

能。`bot.py` 只依赖一个 `handle(sender, text)` 接口；`adapters/feishu.py` 是参考实现。
Slack/Teams/Matrix/本地 HTTP webhook 都可以照抄一个适配器。

如果连 IM 都没有，用 CLI：`ai4s bot handle --sender ... "回执 ..."`，
状态存在 `state/tickets.jsonl`，一样能跑。

## 11. 这套东西和 git 怎么分工？

- **代码/文档**：git，PR 评审。
- **数据/大文件**：单源库 + manifest；不要塞进 git。
- **注册表**：git（可 diff、可回滚），发版时生成快照。
- **台账/知识卡**：git；数据文件只引用编号。

一个常见分工：`registry/` 和 `docs/` 进 git；`library/` 在共享盘/对象存储；
`manifest.tsv` 定期备份，`verify` 是它的测试。

## 12. 数据要保留多久？

按你所在机构/行业的合规要求。技术上的默认建议：

- **不删除**：作废也留件，只标记。
- **保留原始 + 至少一个校验副本**：开卷快照 + 异机副本；保多久、谁验、多久验一次要拍板。
- **如果暂时没有第二份**：把“库是单点”写进风险记录，而不是当作没人提起的假设。

## 13. Steward 离职了怎么办？

- 所有操作都写成可复制的命令，不靠记忆。
- 每季度让另一个人完整跑一次收库（演练）。
- 签字权交接要留书面记录：旧钥撤销、新钥登记、历史签名仍可验证。
- 触发重新设计的条件写死：出现第二个 Steward，或单日入库 > 1000 文件。

## 14. 怎么证明这套东西有效？

不要用“覆盖率”“文件总数”当 KPI。看五个：

| 指标 | 健康信号 |
|---|---|
| ERROR 率 | 逐月下降 |
| 一次通过率 | 上升 |
| 未接住率 | 下降 |
| 复发 | 同类死法关闭后 **0 例** |
| 交付到回执 | 稳定或下降 |

最有说服力的一句话是“**之后 0 例**”——关键在“改完之后没再发生”，不在“我们改了”。

## 15. 会不会过度治理？

会。三个刹车：

1. **只治理会被引用的东西**。调参中间图、一键可重算的临时产物不入库。
2. **规则也会腐烂**。每季度复盘一次“哪些规则可以删”。
3. **MVP 先跑通一批**。不要在第一周就上加密、机器人、知识库、证伪台账。

如果一套规则让 owner 每次交付多花半天，而收益只是“看起来整齐”，删掉它。

## 16. 这套东西的科学结论可信吗？

不。这套东西只保证：

- 文件可解析、可追溯、没被动过；
- 码的含义被签过字、改过就失效；
- 算出来的东西有来源链和实名复核；
- 被推翻的结论有地方待、能被查到。

**它不保证科学正确。** PASS 是“没踩到已知的坑”，不是“这批东西是对的”。
科学正确性要靠证伪流程、复现、同行评审，以及人。
