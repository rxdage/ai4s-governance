# 07 · 证伪：结论入库前的对抗复核

> 一个结论从“跑出来”到“写进报告”，中间会经过报告 → 规格书 → 摘要 → PPT → 客户答复
> 四五次转述。转述中必然发生三件事：口径被丢掉、未知被四舍五入成已知、
> 已被自己推翻的结论继续活在旧文档里。
>
> 这一节是一套**把“证伪”变成固定动作**的流程，不是一句“要严谨”。

## 1. 规则

**任何结论，只有活过一轮“默认推翻”的独立复核，才能进入 `RESULTS.md`、handoff 页、
SOP、模型卡或作废台账。**

- 触发：本批数据推出 ≥3 条带数字的结论，准备写 RESULTS/台账/handoff 时。
- 不触发：纯代码 review；只是引用已入库的旧结论（直接查台账）。

真实团队在两个月里**自我推翻 7 次**，其中 5 次的直接原因就是“一个看起来合理的数
被下游当成了实测”。这套流程是那 7 次的学费。

## 2. 第一步：先查台账

每条待复核结论里的数字和说法，先 grep 作废台账（`claim` / `correction` 字段）。

命中的直接按台账的 `correction` 处理，**不进复核队列**——已作废的东西不需要再花
agent 推翻一次。

```bash
ai4s ledger query examples/ledger/deprecations.yaml --contains "6.1"
```

## 3. 第二步：把结论写成可证伪的单句

逐条写成**含具体数字、口径、来源文件**的单句，编号 `C1…Cn`，分两档：

### 承重（load-bearing）：3 个视角各查一遍，多数决

满足任一即承重：

- 会写进台账 / SOP / handoff 页 / 采购决策依据
- 带 `±`、`σ`、`R²`、置信区间等统计声明
- 含物理解释或身份判定（“R0 就是 R_s”“这是 CPE”“主因是……”）
- 含优先权或方法学声明（“首次测出”“该方法可用于”“无漂移”“已解除”）
- 与既有台账条目呼应或矛盾

### 支撑（supporting）：1 个怀疑者

其余数字性陈述（标定常数、对照结果、旁证一致性）。

## 4. 第三步：配视角

每条承重结论配 3 个**互不相同**的视角，写成一句具体指令，而不是标签：

| 视角 | 该问什么 |
|---|---|
| 统计 | 自由度算对没有；误差棒是条件误差还是完整协方差；参数数不同的模型比较是否公平（AICc/BIC/嵌套 F）；显著性有没有被 df 和参数不确定度传播压低 |
| 数值 | 独立重跑拟合；网格搜索是否到全局最优；换口径（子集、去首点、平移时间零点）参数跳多少 |
| 物理 | 函数形式对这个体系合不合理；参数落不落在物理可能范围；极限论证（t→0、ω→∞）成不成立 |
| 外推风险 | 观测窗和被声称的物理过程时标差几个数量级；外推到窗外的量对模型形式有多敏感 |
| 公平性 | 被证伪的模型有没有被绑住手脚（不给漂移项、不给全数据重拟合、不放开 τ 的置信区间） |
| 设计/混杂 | 实验设计能不能分辨两个因子；全集共线性多少；样本量（n=1 装配？）撑不撑得起方法学结论 |
| 反例 | 构造一个相反机制的情形，看它能否也产生这组数据 |
| 概念 | 被命名的量在这个测量里到底是什么的和；2 线/4 线、接触电阻、量程限幅 |
| 对照 | 与项目内其他记录是否矛盾；声称的“一致”是否只是巧合 |

另配 **3 路查漏（gaps）**，固定三问：

1. 这批数据还支持哪些**尚未做过**的分析（逐点残差、被丢弃的点、status 列、时序异常、配对差值）
2. 有哪些**未经检验的隐含假设**（线性拟合、指标定义、丢点正当性、接法、量程），
   逐条说怎么使结论失效
3. 哪些表述有**过度声称**风险（身份判定、单装配谈方法学、优先权），给保守替代表述

## 5. 第四步：写 PREAMBLE

PREAMBLE 必须让一个**零上下文**的 agent 能独立干活：

- 原始数据目录、每个文件是什么、格式（元数据行、表头、点数、扫描结构）
- 被测件与接法
- 运行环境与坑（编码、数值库版本、缺哪个包）
- 原分析的**口径**（怎么取点、怎么定义量），并明说“你可以质疑这个口径”
- 原分析的**汇总表原样贴进去**，要求 agent 先复算它——复算不出汇总表本身就是一条判决
- 纪律：agent 引用的任何脚本必须存到 `review/scripts/`，**不得指向临时目录**
- 脚本命名必须带视角号（`C3_L2_fit.py`），否则两个视角会互相覆盖

## 6. 第五步：跑

规模参照一次真实复核：

| | |
|---|---|
| 承重 | 6 条 × 3 视角 = 18 |
| 支撑 | 6 条 × 1 = 6 |
| 查漏 | 3 |
| 合计 | **27 个 agent** |
| 成本 | 约 256 万 token、343 次工具调用 |

判决结构 `VERDICT` 七个字段缺一不可：

```
claim_id / refuted / confidence / what_i_computed /
reasoning / corrected_statement / caveat
```

- `what_i_computed` 必须是具体数值。
- `caveat` 即使不推翻也要填——“必须随附的限定”是入库时要一起写的。

汇总规则（写死在模板里）：

- 承重：`refuted ≥ 2/3 → 推翻`；`= 1/3 → 有异议`；`0 → 通过`。
- 支撑：单票。

## 7. 第六步：落盘（四个文件，顺序固定）

1. `review/verification_raw_<date>.json`：workflow 返回值原样存
   （含 summary / agentCount / result / workflowProgress / totalTokens / totalToolCalls）。
2. `review/FALSIFIED.md`：判决总表 → 承重逐条（原表述 / 视角 i 判决 / 实际复算 / 理由 /
   更正表述 / 必须随附的限定）→ 支撑逐条 → 查漏（可用现有数据回答 / 需要补测）。
   渲染后人工通读一遍，**只修错字，不改判决**。
3. `deprecations_draft.yaml`：每条“推翻”或“更正”写一条 `DRAFT-nn`，字段与主台账一致。
   - `verdict` 里写票型和三重错误的编号，数字全部来自 `what_i_computed`。
   - `caveats` 必须收进**幸存的部分**（例如“幂律函数形式本身没被推翻，
     被作废的是参数值和物理解释”）——否则下次有人会把整条方向一起扔掉。
   - “有异议”的条目不进草稿，进 RESULTS 并带 ⚠ 和异议视角的原话。
4. `RESULTS.md`：重写：顶部横幅写“n 条初稿 m 条被推翻，只保留幸存部分，
   引用前先查 FALSIFIED.md”；正文只留幸存结论并按更正表述改写；
   末尾加“**明确不能说的**”表（不得写 / 为什么），每行一条被推翻的原话。

## 8. 第七步：并入台账（可以隔天）

- `DRAFT-nn → DEP-<域>-<下一号>`，下一号 = **该域当前最大号 + 1**，连续不留缺号。
  - ⚠ 不要用“总条数 + 1”：总数里含其他域，会跳号。
- 文件头“来源 N”加一行；`source` 写 `<results>/review/FALSIFIED.md §Cx`。
- `residue` 列出旧值仍散落的文件（旧 RESULTS、handoff 页、commit message），巡查一遍。
- 草稿文件头改成“✅ 已于 <日期> 并入，编号 …，本文件保留为快照”。
- 与既有条目同源的（不同方法独立复现同一原理）在两边 caveats 互相指。
- 只提交到本地分支；**发布动作由人做**。

## 9. 台账字段

```yaml
deprecations:
  - ext_id: DEP-CAL-003
    claim: "标定常数 k = 1.21，误差 ±3%"
    status: 作废                  # 作废 | 更正 | 部分平反
    date: 2026-03-04
    verdict: >-
      汇总表用的是全量数据，但 k 是在去掉首点后拟合的；复算全量给 1.08，
      差 11%。另外 ±3% 是条件误差，不是完整协方差。
    correction: >-
      全量重拟合 k = 1.08 ± 0.06（95%）；旧 1.21 只能用于“去掉首点”口径。
    caveats: >-
      幂律函数形式本身没被推翻，被作废的是参数值和“±3%”这个精度声明；
      趋势与量级仍成立。
    residue:
      - results/old/RESULTS.md
      - handoff/CONTEXT_PACK.md §2
    scope: "仅老款夹具 + 银电极；新款未测"
    source: "results/2026-03-04/review/FALSIFIED.md §C2"
```

规则：

- `status=部分平反` 必须写 `scope`：平反只对哪个范围成立。
- `caveats` 必须回答“那什么还站得住”。
- `residue` 是防复活巡查点；台账是写给下一个读旧文档的人看的，不是写给自己看的。

## 10. 纪律（复核者和整理者都适用）

1. **从原始文件算，不从汇总表算。** 汇总表是被审对象。
2. **默认推翻。** “听起来合理”不是通过理由；只有自己重新推出同样结果才 `refuted=false`。
3. **“无法复现”本身就是推翻。** 一个数字若穷举口径都得不到，判推翻并记下最接近的口径。
4. **误差棒要问是条件的还是完整的。** 网格搜索出的参数当常数用，是最重的一类错。
5. **df 要一致。** 参数数不同的模型比 σ 前先对齐自由度。
6. **两个数凑巧相等不是互证。** 先查它们各自的定义是不是同一个量。
7. **优先权声明自动承重。** “首次”“唯一”“直接测出”出现即升档。
8. **只能说“未检出”，不能说“不存在”。** 给出功效或稳健区间。
9. **幸存部分要写明。** 推翻参数不等于推翻方向。
10. **措辞纪律。** 不许说“原模型不收敛”——要说“同一个错模型收敛到另一个值”；
    不许说“真实器件没有 X”——要说“本类模型不支持 X 这个数”。

## 11. 什么时候值得跑

| 场景 | 建议 |
|---|---|
| 要写进对外报告/采购决策 | 必须跑，承重 ×3 |
| 内部周报里的数字 | 至少 1 个怀疑者 |
| 探索性分析、只看方向 | 不跑；不要写进 RESULTS |
| 复现别人的结论 | 先查台账；命中就引用 correction |

成本不低（27 个 agent 约 256 万 token），所以**只对承重结论跑**。
把“每条都跑”当成目标是另一种形式主义。

## 12. 反模式

- ❌ 先写 RESULTS，再补一个“复核”章节。
- ❌ 让提出结论的同一个 agent 复核自己。
- ❌ 把“无法复现”记成“数据质量问题”，然后继续引用。
- ❌ 台账只写“作废”，不写 correction 和 caveats。
- ❌ 不扫 residue，旧数字继续活在 handoff 里。
- ❌ 把“有异议”当成“通过”。

## 13. 检查清单

- [ ] 每条承重结论都有 3 个不同视角，且视角要写成具体指令，不要只写标签。
- [ ] PREAMBLE 能让零上下文 agent 独立干活。
- [ ] 判决七字段齐全，`what_i_computed` 是数值。
- [ ] `caveats` 写了幸存部分。
- [ ] `RESULTS.md` 有“明确不能说的”表。
- [ ] 台账编号按域递增，无跳号。
- [ ] `residue` 已巡查。
- [ ] 发布前有人通读 FALSIFIED，只改错字。
