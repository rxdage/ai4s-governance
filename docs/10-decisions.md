# 10 · 设计决策与被否方案

> 一份只写“我们采用了什么”的文档没有用。真正帮别人复用（或反驳）的是：
> **当时有哪些选项、为什么没选、代价是什么。**

## A. 核心决策

### D1 · 规范即代码：YAML 是唯一真值

- **背景**：规范文档会被人改、被复制、被局部引用；三份文档出现两个版本是常态。
- **选项**：① 只写 Markdown；② 只写 JSON Schema；③ Markdown 解释 + YAML 机器契约。
- **决定**：③。文档与 YAML 冲突时 YAML 赢；解析器从 YAML 读正则、上限、保留字。
- **代价**：非技术同事要能看懂 YAML 的一小部分；改规则要同时改文档（CI 可以查链接，查不了语义）。
- **收益**：机器契约不会和实现漂移；`selftest` 能证明规则真的生效。

### D2 · 四区制，而不是数据库或标签

- **选项**：① 数据库 + 元数据表；② 文件系统 + sidecar 标签；③ 文件名四区 + 注册表。
- **决定**：③。
- **理由**：小团队没有 DBA；备份、迁移、给外部拷贝都不该依赖某个服务。
  文件名是唯一在“复制/压缩/上传/发微信”之后仍然活着的元数据。
- **代价**：名字变长；改语义只能靠“换号重入”，不能原地 UPDATE。
- **不选数据库的理由**：服务挂了、导出丢了、权限配错，任何一条都会让数据“在但找不到”。
- **不选纯 sidecar 的理由**：sidecar 会被漏拷、会被改名、会和数据分家；名字不会。

### D3 · 类型与条件分开，条件只写 class+数字

- **选项**：① 所有参数进名字；② 参数全进 sidecar；③ 类型码 + 条件 class/code + instance 在注册表。
- **决定**：③。
- **理由**：参数进名字会爆炸且无法排序；参数全进 sidecar 则“不打开文件就不知道是什么条件”。
- **代价**：查具体参数要查注册表；注册表必须可检索。

### D4 · 签字绑定内容哈希（公开版硬化）

- **背景**：条目里写 `status: APPROVED` + `approved_by`，改内容后标签还在；
  AI 可以把 `approved_by` 填成称谓；没有人能证明“批准的是哪一版”。
- **选项**：① 继续用内联 status；② 签字时把条目复制一份快照；③ 签名记录 `content_sha256`。
- **决定**：③。
- **代价**：读的时候要 join 两个文件；每次签字多一条记录。
- **收益**：改一个字符签名自动失效；撤销是事件，不删历史；“假 APPROVED”在结构上不可能。
- **与内部版的差异**：内部版仍靠 `status` + 人工 unsign；公开版把它变成机器不变量。

### D5 · 复制入库，不用移动、不用硬链接

- **选项**：① 移动；② 硬链接；③ 复制 + sha256 + 只读。
- **决定**：③。
- **理由**：移动会让 owner 的工作目录失去原件；硬链接在跨文件系统/备份/权限上处处是坑；
  复制最笨，但“库里的字节”和“来源的字节”可以独立验证。
- **代价**：占双份空间；复制 3000 个文件会慢，也会在崩溃时留下半成品（用“每落一个写一行”解决）。

### D6 · data / derived 分区

- **选项**：① 混放，用文件名区分；② 分目录，用类型码的 `derived` 标志自动分流。
- **决定**：②。
- **理由**：几个月后没人分得清“测的”和“算的”；标志位是机器判的，比人记规矩可靠。
- **代价**：注册时必须回答“这是测的还是算的”；判不准要按 true 报（宁可多一道复核）。

### D7 · 入库后永不原地改

- **选项**：① 允许覆盖；② 允许原地改 + 版本号；③ 库外改好、同 T、RUN+1、整份重入。
- **决定**：③。
- **理由**：覆盖会毁掉“当时用的是哪一版”；版本号要额外维护一套映射；
  RUN+1 让旧引用天然有效（旧文件还在、内容没变）。
- **代价**：库里会有多个版本；要靠台账和作废清单回答“现行版是哪个”。

### D8 · 作废留件，不删除

- **选项**：① 删除；② 移到 `_archive/`；③ 原地只读 + 作废清单。
- **决定**：③。
- **理由**：删除不可逆；移动会让路径引用悬空；留件 + 清单让“历史事实”和“现行状态”分开。
- **代价**：存储会涨；需要清单来回答“哪个是现行版”。

### D9 · 程序判定 PASS，AI 只负责跑

- **背景**：AI 整理过的交付仍然有 145 个语法错、192 个未注册码。
- **决定**：`exit code 0` + `_credential.txt` 才算 PASS；AI 的“应该能过”不算。
- **代价**：要维护检查器；检查器本身可能错（所以它也要测试与版本）。
- **边界**：PASS 只证明“没踩到已知的坑”，不证明“科学正确”。

### D10 · 决定在人，操作在 AI

- **决定**：签字、抽查、放行、语义判断、发消息归人；跑工具、产清单、改授权文件归 AI。
- **判据**：错了还能改回去 → AI 可做；错了不可逆 → 只有人能做。
- **代价**：人仍然是瓶颈；但这套系统的目的是“人只做只有人能做的那部分”，“无人”不是目的。

### D11 · 机器人只做四件事

- **决定**：回执、放行/拒收、豁免、解释。不做签字、不做复制、不主动 @ 人。
- **理由**：机器人的每一行代码都会变成组织流程；命令面越小，越不会长出“机器替人决定”的暗门。
- **代价**：复杂沟通仍要人；但复杂沟通本来就不该由机器人做。

### D12 · 不做 Web 看板

- **选项**：① 自建看板；② 机器人定时播报 + manifest 查询；③ 什么都不做。
- **决定**：②。
- **理由**：看板是另一个要维护的系统、另一套权限、另一个会过期的真相；
  对小团队，**群里的播报 + 一份 manifest** 已经能回答“谁欠什么”。
- **代价**：没有可视化趋势；需要时用一条 SQL/脚本从 manifest 生成。

## B. 被否的方案（以及为什么）

| 被否方案 | 当时的主张 | 为什么没选 |
|---|---|---|
| 新建“交付_YYYYMMDD”中转夹 | 收库人知道该收哪些 | 实测三次都失败；复制 5.6 G 引入中断/覆盖风险，收益为零；改成“声明根 + 交付清单” |
| 用两个数字对账（不生成清单） | 不改代码，先用数量对 | 收库人扫的目录只要是超集，两个数就对不上；没有可复核口径 |
| 清单指纹用绝对路径 | 简单 | 跨机必不相等；改成 basename + size，重名由 `NAME_DUPLICATE` 兜住 |
| 库内再加一层目录 | 结构更清楚 | 只对达到新批次的生效、老批次原样，看似可逆；但 MAX_PATH 只剩一层余量，且平铺是“同名必撞”的保护 |
| 排除所有 `_` 开头目录 | 一键屏蔽 `main/` | 会让 owner 自己的 `_待上传/` 对工具隐形；改成“只扫声明根” |
| 让 AI 自动改名 | 省人力 | 改名动真实数据，原名留档不可逆；AI 只能产清单 + 预演，人点头才 apply |
| 让 AI 代签 | 快 | 曾导致整批 162 条签字撤销；签字键必须本人 |
| 自动补 RUN 断号 | 让检查全绿 | 那是伪造采集轮次；WARN 只能答，不能改 |
| 自动清空 REGISTRY 滞留 | 让巡检好看 | 滞留 = 已入册未清夹，清夹是 owner 的动作；机器只能点名 |
| 默认开启加密 | 安全 | 公开版没有组织密钥体系；强加会给 fork 制造“加密了但打不开”的坑 |
| 全自动收库 | 省 Steward | 带旗批次（打回/待人判/知情收）永远需要人；规则放行也必须是人签过的规则 |

## C. 公开版与内部版的差异

| 维度 | 内部版 | 公开版 | 为什么 |
|---|---|---|---|
| 签字 | 条目内 `status` + 人工 unsign | `signatures.yaml` 绑定内容哈希 | 把“记得重签”变成机器不变量 |
| 编号起点 | 硬编码历史批次分界 | `zero_allowed_from` 可配置 | 别的团队没有这段历史 |
| 加密/密级 | age 加密、双哈希账本、解密抽查 | 只留 `classification` 接口位 | 不把组织密钥体系强加给 fork |
| 机器人 | 飞书卡片 + 机器人 + 定时任务 | 适配器接口 + 飞书参考实现 | 别人不一定用飞书 |
| 看板 | HTML 看板 | 删除；群播报 + manifest | 少一个要维护的真相 |
| 文档 | 中文、内部术语 | 中文正文 + 英文入口 | 对外可达 |
| 数据 | 真实批次/参数 | 全合成 demo | 脱敏 |

## D. 如果你要推翻这些决定

欢迎。但请连代价一起写：

```markdown
### D-x · 标题
- 背景：
- 选项：
- 决定：
- 代价：
- 什么条件下应该重新考虑：
```

最后一行最重要。没有“重新考虑的条件”，决策就会变成教条。
