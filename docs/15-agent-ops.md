# 15 · Agent 运营：任务路由与收敛环

> 这一篇先放下数据治理，讲 agent 怎么干活不烧钱、不反复错。
> 它来自一个很具体的坑：我们用最强的模型改流程，还是不停出错，而且贵。

## 0. 问题不是“模型不够强”

有一段时间，我们的默认做法是：所有事都用最强模型。结果是：

- **贵**：改一个文档、跑一次巡检、重写一段脚本，都按最高档计费。
- **慢**：一个本来 30 秒的机械改动，排队等最强模型。
- **还是错**：改流程是 meta-work，比业务代码更容易“看起来对了”。
  没有验收标准，模型就会在“差不多”的地方停下来。

后来发现，问题不在“最强模型不够强”，在**任务没有分层，循环没有停止条件**。

## 1. 两个发现

### 发现一：任务要分层，不是所有活都值得用最强模型

| 任务类型 | 例子 | 路由 | 为什么 | 护栏 |
|---|---|---|---|---|
| 机械编辑 | 批量改名、格式统一、文档同步、字段重排 | 便宜/快的 harness | 可验证、可回滚 | 先 dry-run，人看 diff |
| 代码/配置改动 | 脚本、CI、schema、模板 | 中等模型 + 测试 | 有测试可判 | 测试必须真的跑 |
| 判断/设计 | 架构、语义、冲突裁决、取舍 | 最强模型 | 需要上下文和推理 | 人做最终决定 |
| 对抗复核 | 证伪、找漏洞、挑假设 | **与作者不同的模型/视角** | 独立性 | 不告诉它“正确答案” |
| 例行检查 | 巡检、对账、生成报告 | 小模型/规则 | 确定性高 | 程序判定，不靠模型 |
| 不可逆动作 | 签字、发布、删除、发消息 | **不路由** | 错了不可逆 | 人 |

一句话：**把对的活给对的模型，不是把所有的活都给最强的模型。**

### 发现二：没有验收标准，循环就会变成聊天

“再改一版看看”通常不会收敛。收敛环需要五个东西：

```yaml
objective: 一句话说清要什么
acceptance: 可执行的检查（命令/测试/清单），不是“看起来对”
max_rounds: 3
budget: token / 时间上限
stop: 通过 / 连续两轮无改进 / 预算耗尽
```

伪代码：

```text
for round in 1..max_rounds:
    run acceptance
    if pass: stop
    if last two rounds show no measurable improvement: stop  # stuck
    propose change with the routed model
    apply in a sandbox
    log what changed and the metric
human reviews the final diff
```

三条规则：

1. **没有 acceptance 的循环不要开。** 先写“怎么算过”，再让模型动手。
2. **改的人不能当裁判。** 同一模型既改又判，等于自己给自己签字。
3. **连续两轮没有可测改进就停。** 换任务、换模型，或者找人；不要用“再试一次”烧预算。

## 2. 一个很典型的反例

一个很典型的反例：用最强模型重写一段流程文档。它每一版都“更完整”，但：

- 验收标准是“读起来顺”，不是“新同事能照着做”；
- 改了几轮，每轮都加内容，没人删；
- 最后文档更长了，新同事还是问同一个问题。

后来把 acceptance 改成三条可执行的：

1. 新同事能在 10 分钟内跑完 demo；
2. 三个命令的输出与文档一致；
3. 一个没看过原文的人能复述“先做什么、后做什么”。

很快就收敛了。模型没变强。是“过”的定义变清楚了。

## 3. 成本指标：看“接受一个改动”的总成本

不要只看 token 单价。看：

| 指标 | 定义 | 为什么 |
|---|---|---|
| Cost per accepted change | 总花费 / 被接受的改动数 | 被拒绝的轮次也算钱 |
| Rounds to converge | 从开始到通过几轮 | 衡量 acceptance 写得好不好 |
| Rework rate | 接受后又被回滚的比例 | 衡量“看起来对了” |
| Time to converge | 墙钟时间 | 人等的是时间，不是 token 单价 |
| Human minutes | 人花在 review/裁决上的时间 | 最贵的通常是人 |

一个便宜的模型如果 5 轮才过，可能比强模型 1 轮更贵。
**路由的目标是总成本最低，不是用便宜模型。**

## 4. 什么时候不要路由

- **不可逆动作**：签字、发布、删除、发消息。没有“重试”。
- **科学判断**：这个数对不对、这个解释成不成立。模型可以提假设，不能背书。
- **对抗复核**：需要独立性；让作者模型复核自己，等于没复核。
- **组织/人际判断**：谁该负责、怎么跟同事说。模型没有上下文。

## 5. 和治理的关系

同一套原则，只是对象从“数据”换成了“agent 的工作”：

| 数据治理 | Agent 运营 |
|---|---|
| PASS 由程序判定 | 收敛由 acceptance 判定 |
| 签字绑定内容哈希 | 改动绑定 diff + 测试 |
| WARN 只能答不能改 | 模型不能自己判“过了” |
| 不可逆动作归人 | 不可逆动作不路由 |
| 作废留痕 | 回滚留痕 |

所以这一篇不是跑题。它回答的是同一个问题：**哪些事交给机器，哪些事必须留给人，怎么证明机器真的做对了。**

## 6. 最小落地

1. 先写 **3 条 acceptance**：命名解析全绿、`ai4s check` PASS、`ai4s ingest verify` OK。
2. 先分 **2 类任务**：机械编辑 vs 判断。不要一上来分十类。
3. 先设 **3 轮上限** 和一个小预算。
4. 记录 **cost / rounds / rework**；两周后看数据，再调路由。
5. 任何不可逆动作，从路由表里删掉。

## 7. 诚实边界

- 模型路由会随供应商、版本、价格变化；**不要把某家模型写死**。
- 便宜模型在长上下文、跨文件冲突、隐含约束上会翻车；用测试和 diff 兜底。
- 收敛环不能保证“对”，只能保证“过了你定义的验收”。
- 最强的模型也会错；区别在于，强的模型错得更像对的。所以**验收标准比模型选择更重要**。
