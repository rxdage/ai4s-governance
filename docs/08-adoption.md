# 08 · 采用路线：30 / 60 / 90 天

> 不要从“制定一份完整规范”开始。从**一批让你真的痛过的数据**开始，
> 用一次真实的交付把闭环跑通，再扩。

## 1. 先判断你该不该做

| 信号 | 适合 | 不适合 |
|---|---|---|
| 同一类文件有 3 种以上命名 | ✅ | 只有一种，且机器已能读 |
| 有人问“这个数是测的还是算的” | ✅ | 从没人问 |
| 结论被推翻过，但旧文档还在引用 | ✅ | 没有对外交付 |
| 每次找数据靠问人 | ✅ | 有成熟 LIMS/ELN 且覆盖全部数据 |
| 团队 < 3 人且数据 < 1 万文件 | ⚠ 先做最小版 | 全套流程会压垮人 |
| 没有稳定样品编号 | ❌ 先解决编号 | 命名只是把混乱写得更整齐 |

## 2. 最小可行治理（MVP，1–2 周）

只做四件事：

1. **一份机器契约**：四区文法 + 20 个类型码 + 5 个条件 class。
2. **一个注册表**：三张 yaml + 一个签字人。
3. **一个交付闸门**：`selfcheck` 能跑、能出凭据、能答 WARN。
4. **一个单源库**：`data/` + `derived/` + `manifest.tsv` + `verify`。

先不要：加密、机器人、看板、知识库、证伪台账。这些是第二、三阶段。

**验收标准**：拿一批真实数据，从“文件名乱七八糟”走到“PASS 凭据 + 入库 + verify 全绿”，
全程有一个人能独立复述。跑不通就不要扩。

## 3. 30 天：把一批数据收进来

| 周 | 动作 | 产出 |
|---|---|---|
| 第 1 周 | 词汇扫描：把现有文件名分词、统计槽位覆盖率；找 3 个最痛的点 | 一页扫描报告（不是规范） |
| 第 2 周 | 定四区语义、编号起点、cutoff；写 20 个类型码与条件 class；选 Steward | `filename-schema.yaml` + 注册表草案 |
| 第 3 周 | 用 20 个真实文件做 dry-run 改名；改工具措辞；让 owner 自己跑一遍 | 改名日志 + 第一版自查包 |
| 第 4 周 | 选**一批**真实数据完整走：自查 → 凭据 → 交付 → Steward 抽查 → 入库 → verify → 回执 | 第一个 PASS 批次 + 台账 |

**第 4 周的批次要小**：10–50 个文件，包含至少 1 个衍生文件。
先别想着收完。目标是“闭环跑通、每个人知道自己在哪一步”。

### 第一周扫描怎么做

```bash
# 只取 basename，不打开文件
find <data-root> -type f -printf "%f\n" > names.txt
# 按分隔符切词，统计 token 频率与槽位覆盖率
python scripts/scan_names.py names.txt
```

扫描只做归纳，**不下裁决**。所有“疑似”标注，没有把握的写“需人工确认”，不编。

真实案例：扫描 175 万文件后才发现，某个人的条件全写在**目录名**里，文件名 87% 是纯序号——
如果先写规范再扫描，会设计出一套根本落不了地的字段。

## 4. 60 天：把节奏跑起来

- 固定收库日（每周一/五），固定回执格式。
- 巡检：谁缺凭据、谁有 ERROR、谁有未答 WARN、字典夹是否滞留。
- 周总结：只回答“这周是在往前走，还是原地重做”。
- 引入“死法归类”：每类失败有关闭标准（之后 0 例）。

**验收标准**：连续 3 周，收库不需要 Steward 临时写脚本；回执发出后有人按格式回；
周总结的“上周待办”完成率 > 50%。

## 5. 90 天：把认知层接上

- 选 3–5 个**承重结论**跑一次对抗复核（不需要 27 个 agent，先 1 条 × 3 视角）。
- 建作废台账，把已知的“死结论”录进去（先 10 条）。
- 给每个模型/知识卡写置信级别与“不能说什么”。
- 对外交付包：上下文包 + 资产分级 + 系统提示词。

**验收标准**：有人引用一个旧数字时，能在 1 分钟内查到台账并给出 correction；
一次复核至少推翻 1 条自己原本要写进报告的结论。

## 6. 角色怎么分（小团队现实版）

| 团队规模 | 建议 |
|---|---|
| 2–5 人 | 1 个 Steward（可兼 owner）+ 每人 1 个 AI；签字与抽查必须是同一人，但**不能是被审的人** |
| 6–15 人 | Steward 半职；加 1 个评审人（衍生/模型）；owner 按项目分组 |
| 16–50 人 | Steward 全职；按项目设 data owner；注册表变更走双人复核 |

**单点风险**：Steward 一个人扛全部复杂度，没有 plan B。缓解：

- 所有操作写成可复制的命令，不靠记忆。
- 每季度让另一个人完整跑一次收库（演练，不是交接）。
- 触发重新设计的条件写死：第二个 Steward，或单日入库 > 1000 文件。

## 7. 培训：不要讲规范，讲三个动作

1. **我的文件该叫什么**：拿他自己的 5 个文件现场改名。
2. **交之前跑什么**：`ai4s check`，直到 PASS。
3. **收到卡怎么回**：一题一行，只认选项。

每人的 AI 也要培训：把 [04-roles-and-ai.md](04-roles-and-ai.md) 第 8 节的指令块
贴进它的系统提示词。**不要指望人记住全部规则；把规则写进工具和提示词。**

## 8. 常见失败模式

| 失败 | 症状 | 对策 |
|---|---|---|
| 先写一本规范 | 三个月没落地，大家继续用旧名 | 先用一批数据跑通闭环 |
| 一次全量迁移 | 改了几万个文件，错了一半，没人敢用 | 按批次迁移 + cutoff |
| 工具太聪明 | 自动改名、自动补号、自动答 WARN | 工具只提示、只记录；决定归人 |
| 没有 Steward | 谁都签字，等于没人签 | 一个人、一把钥匙 |
| 只考核覆盖率 | 为了指标把垃圾塞进库 | 考核 ERROR 率、一次通过率、复发 0 例 |
| 没有回头看 | 周总结变成流水账 | 固定第 6 节“上周说要做的，做了没” |

## 9. 成本估算

| 项 | 一次性 | 持续 |
|---|---|---|
| 规范 + 注册表 | 3–5 人日 | 每周 1–2 小时审提案 |
| 工具部署 | 1–2 人日 | 每月 2–4 小时维护 |
| 每批交付（owner） | 首次 0.5–2 人日 | 每批 10–30 分钟 |
| 收库（Steward） | 首次 1 人日 | 每批 20–60 分钟 |
| 对抗复核 | — | 每季度 1 次，按承重条数计 |

最贵的是**前两周把语义吵清楚**，工具本身不贵。这一步省掉，后面全是返工。

## 10. 什么时候可以停

- 连续 3 个月一次通过率 > 80%，未接住率 < 5%，复发 0 例 → 可以只保留巡检与台账。
- 出现新的数据类型/新设备 → 重新走一次“类型码 + 条件 class”的小循环。
- 团队规模翻倍 / 出现第二个收库人 → 重新设计权限与库结构，不要在原结构上硬加。
