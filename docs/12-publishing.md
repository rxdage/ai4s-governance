# 12 · 发布前脱敏检查清单

> 目标：把一套在内部跑通的系统，变成别人可以读、可以 fork、不会泄露当事人/单位/工艺的公开仓库。
> **脱敏的重点是逐类确认**：这条信息是否必要、是否可推断、是否可组合还原；换名字只是其中一步。

## 1. 先决定“发什么”

| 内容 | 建议 | 理由 |
|---|---|---|
| 规范、机器契约、工具、模板 | ✅ 发 | 复用价值最高 |
| 方法论文档、案例数字（量级） | ✅ 发（脱敏后） | 可信度来源 |
| 真实批次号、样品编号、器件参数 | ❌ 不发 | 可还原具体项目 |
| 真实人名、账号、IM 群 ID、open_id | ❌ 不发 | 隐私 |
| 内网 IP、主机名、NAS 路径、共享盘名 | ❌ 不发 | 攻击面 |
| 供应商、外协厂、合同号、报价 | ❌ 不发 | 商业 |
| 客户/合作方名称、未公开 KPI | ❌ 不发 | 商业 |
| 密钥、token、私钥、口令 | ❌ 绝不 | 安全事故 |
| 真实实验图片/PDF | ⚠ 逐张看 | 可能带水印、页眉、条码、元数据 |
| 内部会议纪要原文 | ⚠ 重写 | 常含人名、决策上下文、情绪 |

**默认原则：能重写就不复制。** 我们这套公开版是重新写的，不是从内部仓库批量拷贝后替换字符串。
重写能同时去掉“上下文泄露”和“文风不适配”。

## 2. 六类必查

### 2.1 人

- 真实姓名、花名、拼音、缩写、账号、邮箱、IM open_id、头像。
- 文档里的“某人说”“某哥”“领导”“合伙人”——改成角色（Owner / Steward / Reviewer）。
- Git commit author / committer；`.mailmap`。
- Office 文档的 `dc:creator` / `lastModifiedBy`；PDF 的作者字段。

### 2.2 组织

- 公司名、产品名、实验室名、部门名、项目代号。
- 统一社会信用代码、合同号、采购单号、发票号。
- 网址、公众号、GitHub org、Docker 镜像名。

### 2.3 位置

- 私网 IP、公网 IP、主机名、用户名、SSH 别名、端口。
- `\\server\share`、`smb://`、`/mnt/nas/...`、`C:\Users\<name>\...`。 <!-- scan:allow 这一行是模式示例，不是真实路径 -->
- 云厂商 bucket、region、实例 ID、VPC。

### 2.4 技术与商业

- 器件结构/工艺参数（厚度、掺杂、孔径、温度、电压）——如果它足以还原你的产品。
- 供应商、外协厂、仪器型号 + 序列号。
- 未公开的 KPI、良率、成本、报价、客户名。
- 真实失效案例（可能被反向识别）。

### 2.5 凭证

- `sk-`、`ghp_`、`xoxb-`、`AKIA`、`Bearer <token>`、私钥头、`.env`。
- CI secret 名称也算线索（`SCSM_REPO_TOKEN` 这种），建议连名字一起去掉。
- Git 历史里的旧密钥：**删文件不等于删历史**；要么重写历史，要么换钥。

### 2.6 可组合还原

单个字段看起来无害，组合起来能定位：

- “5 人团队 + 某大学 + 某设备型号 + 某月流片” → 基本能查到人。
- “某供应商 + 某合同号 + 某金额” → 商业信息。
- 时间线 + 批次号 + 地点 → 具体项目。

处理：**打散组合**。保留量级（“百万文件”“117 条作废”），去掉能拼出个体的细节。

## 3. 自动扫描

仓库自带一个 tripwire：

```bash
python scripts/scan_sensitive.py --path . --terms /path/to/terms.txt
```

`terms.txt` 一行一个敏感词（真实人名、公司、产品、供应商、主机名），**不要提交**。
脚本会报：私网 IP、UNC 路径、home 目录、NAS 挂载、邮箱、手机号、
API key 形状、私钥头、`password=`、Office 元数据、以及 terms 命中。
若某一行本身就是“模式示例”（比如本文上一节），在行尾加 `<!-- scan:allow 理由 -->`。

它**不检查**图片、PDF、git 历史、二进制。那些必须手工。

## 4. 手工检查

- [ ] **图片**：逐张打开。看水印、页眉、条码、屏幕上的文件名/路径、反射、头像。
- [ ] **PDF**：看属性（作者/标题/公司）、页眉页脚、嵌入字体名、附件。
- [ ] **Office**：文件 → 信息 → 检查文档 → 删除个人信息；或重新生成。
- [ ] **Notebook**：输出单元格里可能带绝对路径、用户名、内网 URL、dataframe 内容。
- [ ] **日志/报错**：栈里常有绝对路径、主机名、用户名。
- [ ] **Git 历史**：`git log -p` 搜敏感词；必要时用 `git filter-repo` 重写，或干脆重新 `git init`。
- [ ] **依赖锁文件**：私有 registry URL、token。
- [ ] **CI 配置**：secret 名称、私有仓库名、跨仓 token。
- [ ] **演示数据**：确认是合成的；人名用 `Owner A`、`Demo Reviewer`，不要用真名谐音。

## 5. 文案检查

- [ ] 没有“我们公司”“我们的产品”这类可定位表述；用“本案例”“某团队”。
- [ ] 数字是量级或已脱敏的比例；没有“2026-08-03 某批次”这种可对上号的时间+批次组合。
- [ ] 失败案例只保留“失败类型 + 后果”，不保留当事人。
- [ ] 不泄露内部系统名（NAS 共享名、机器人名、看板名、内部代号）。
- [ ] 引用第三方内容有出处与许可；没有“待核对”却写成确定。

## 6. 法务与许可

- **代码**：MIT（见 `LICENSE`）。
- **文档**：CC BY 4.0（见 `LICENSE-docs`）。
- **第三方资产**：图片、字体、数据集、模板，逐个确认许可；不确定就不要放。
- **商标**：不要用别人的 logo/产品名做宣传。
- **专利**：公开仓库可能构成现有技术公开；如果内容要申请专利，先咨询。
- **出口管制/数据合规**：涉及人类受试者、医疗、地理、加密的，先过合规。

## 7. 发布流程

1. 在**独立目录**重建公开版（不要在原仓库上删文件）。
2. 写 `README.md`（英文入口）+ `README.zh-CN.md`（中文全文）；GitHub About/topics 用
   [github-listing.md](github-listing.md) 里的现成文案。
3. 跑 `scan_sensitive.py` + 手工清单。
4. `git init` 一个**全新**仓库；不要带上内部历史。
5. 首次提交前 `git status` 逐项看；确认没有 `.env`、数据、私钥。
6. 建 GitHub 仓库（private 先推）→ 再开 public。
7. 开 Issues 模板、`SECURITY.md`、`CODE_OF_CONDUCT.md`。
8. 发布后 24 小时内再扫一遍（有时会忘记 `.github/`、`examples/`）。

## 8. 如果已经泄露了

1. **先止血**：把仓库转 private / 删除 release / 撤销泄露的 token。
2. **换钥**：任何出现过的密钥立即轮换；不要指望“删 commit”。
3. **评估**：泄露的是人名、路径、参数还是凭证？影响范围？
4. **通知**：按你们的安全/合规流程；必要时通知当事人。
5. **复盘**：把这次泄露加进 `scan_sensitive.py` 的规则或 terms，写进清单。
6. **重写历史**：`git filter-repo` 或重建仓库；force push 后通知所有 fork。

## 9. 最终检查清单

- [ ] `python scripts/scan_sensitive.py` 0 hit（或每条都显式豁免并写明理由）。
- [ ] `grep -ri` 真实人名/公司/产品/供应商 0 hit。
- [ ] 图片/PDF/Office 元数据已清。
- [ ] git 历史干净（或全新 init）。
- [ ] demo 数据全合成，`Demo Reviewer` 不是真人。
- [ ] LICENSE / LICENSE-docs / SECURITY / CONTRIBUTING 齐全。
- [ ] README 能在一个屏幕内说清“这是什么、给谁、怎么跑”。
- [ ] 所有命令在干净环境跑过一遍（`pip install -e .` + demo + tests）。
- [ ] 案例数字与内部记录对得上（脱敏不等于编数）。
- [ ] 发布后 24 小时复扫。
